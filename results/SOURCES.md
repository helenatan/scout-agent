# Sources of attempts.csv

Generated by `release/scripts/export_public_results.py` (stdlib only, no model or network calls). Paths are relative to the project root. One bullet per source directory; each run record is `<dir>/runs/<run_id>.json`, from which state, outcome_reason, cost_usd, duration_s, token counts (summed over `usage.by_model`), tool_calls (`len(trace.tool_calls)`) and model_requests (`usage.requests`) are taken.

Tool version mapping (code design -> public): baseline v1, redesigned v2, tuned v3, dated v4, v5 v5. Model mapping: claude-haiku-4-5-20251001 haiku-4.5, claude-sonnet-5-5 sonnet-5.5, claude-opus-5 opus-5. Config codes in records were checked against model/design: A haiku+baseline, B opus+baseline, C haiku+redesigned, D opus+redesigned, E haiku+tuned, S-B/S-R/S-T/S-D/S-V5 sonnet+baseline/redesigned/tuned/dated/v5, O-V5 opus+v5.

## Caveats

- Costs are notional (subscription runs via headless Claude Code): the rate card applied to the tokens each run reported.
- `rep` is the rep index inside one results directory; directories ending -1/-2/-3 are independent rounds, so (label, task_id, rep) identifies an attempt, not (task_id, rep).
- The Opus 5 + v1 reference on the original 11 tasks = final-eval config B (33 runs, grader v3 recomputed) + model-pairs mp-OB-* (11 runs).
- Haiku + v2 (132 runs) in the model-pairs report = haiku-lift-r4 variant C (99) + final-eval config C (33). Haiku V0 (135) = r4-V0 dev (63) + hold (36) + fresh-hold (36).
- Haiku variants V0-V3 use tool design `tuned` (exported as v3) plus Haiku-only levers that differ per variant (see experiments/haiku-lift/REPORT-round4.md); the `variant` column carries the variant code.
- fresh-v1: `split` is `all` (the fresh suite has no dev/holdout split). failed_checks lists Part 1 check names that are false plus Part 2 rubric items whose outcome is not pass (none in these files). Runs that did not complete have no Part 1 checks, so failed_checks is empty; see state/outcome_reason. For fresh-v1-opus-v5 the v1 file was produced by the v1 grader with Part 2 skipped for runs that failed Part 1 (as in grade_fresh.py).
- Grader v3 runtime failures carry the check name `runtime_completed` (from autograde.py).
- failed_checks entries are check names only. Some names embed a company name or a posting-id prefix (e.g. `label_walmart_d7b6587a`, `quote_S&P Global`); they are names defined by the graders, not answer text. No name exceeded 64 characters, so none were truncated.
