From your question to a checked answer

Scout asks the model what to investigate, uses tools to gather evidence, and checks the proposed answer before returning it. The same budget and deadline apply throughout.

You ask→Scout gathers evidence→Scout checks the answer→You get the result

    Which events are recorded?
    EventRecorded when
    run_startedThe execution loop picks up a queued run.
    model_requestEach Messages API request, after budget has been reserved for it.
    tool_callEach MCP tool call the loop executes for the model.
    validation_failedThe runtime checks reject a submitted answer.
    repair_attemptedThe current engine records the repair outcome (succeeded or failed), not its start. A repair model request is recorded separately as model_request with its purpose.
    budget_exhaustedA reservation does not fit the remaining budget, so the request is not sent.
    cancel_requestedThe cancel endpoint is called.
    deadline_exceededThe deadline expires, including while queued or with a request in flight.
    cost_unsettledA late failure leaves billing unknown; the reservation remains outstanding.
    cost_settledLate request usage is reconciled; run state and answer remain unchanged. Other requests may still be unsettled.
    run_endedThe run reaches a terminal state.
    What does “completed” guarantee?

    It means the runtime checks passed. Whether the answer is correct is decided by offline grading against an answer key. Each finding declares what it supports: a list of records (the default), a count, or posting text. A records finding must cite its records, with every page of the list read when the task requires complete results; a count may rest on a complete count result instead. The model declares the scope itself, so offline grading still checks that each claim matches it.

    How are the components connected?

    The browser submits a question to Scout’s HTTP API and polls the saved status and events. The execution loop calls the model provider and executes the model’s requests through the local MCP data tools. Scout owns admission, evidence persistence, answer checks, and billing. The model never directly reads the dataset. See the architecture for the component map.

    In the study’s evaluations, model calls went through a headless Claude Code session on a subscription instead of the Messages API. Scout still owned the tools, evidence, answer checks, the one repair and the deadline. Token counting is not available on that path, so the budget and the input ceiling were checked on each request as its usage arrived, and costs are notional: list rates applied to reported tokens.

    At running-state checks, an expired deadline takes precedence if cancellation is also observed. Already-terminal results remain fixed. Reusing an idempotency key with the same payload returns the existing run; a different payload returns a conflict.
