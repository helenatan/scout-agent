Scout architecture

Built and evaluated · PRD v0.36

Scout answers hiring questions over PAI’s saved job postings, and records the evidence and cost of every answer. The study asks whether better tools let a cheaper model meet the same quality requirements. To follow one run from question to checked answer, see the run lifecycle. The code is in this repository; start with the README.

Headline comparison, outlined: Sonnet 5.5 with the final tools against Opus 5 with basic tools. Every attempt uses exactly one model and one tool version; the prompt, budget, deadline, checks, and grading stay fixed. Basic, summary and final tools are product designs; explicit caveats and dated summary were built only for the experiments.

Why redesign the tools? “Is hiring for agent-building skills increasing?” needs more than raw counts:

  • Duplicates inflate counts. One opening can appear across sources or locations.
  • Collection limits distort trends. Missing data can look like declining hiring; zero records do not establish zero openings.
  • Mentions are not requirements. “We build agents” does not mean applicants need agent-building experience.

The later versions move counting into code and attach the collection record to results; the final tools also write each data gap as a sentence the model is told to copy. The model still selects the cohort, interprets requirements, and judges what the evidence supports.

1 · Answer a research question

One run, from the browser to Scout’s backend and back. The model and the data tools are peers called by Scout; the model never touches the data directly.

  • Budget, deadline, or cancellation can stop research or repair early. Partial work is saved and returned as incomplete or cancelled.
  • Runtime checks catch mechanical problems without an answer key. completed never means verified correct; only offline grading judges that.

2 · Evaluate and compare configurations

The evaluation runner exercises the same HTTP API and execution path as an interactive question, then grading and reporting happen offline.

  • Private answer keys are never available to the model, the MCP tools, or the runtime checks.
  • The comparison screen reads saved reports and never launches evaluations. Saved results can be inspected without an API key.

The execution loop calls the three data tools through a separate local server process, one per run. Stdio carries requests and results over standard input and output.
Model connection
Scout calls Anthropic’s Messages API through the Python SDK, or runs the same loop through a headless Claude Code session with Scout’s tools exposed over an MCP bridge. The study used the Claude Code path on a subscription, so its costs are notional. Either way, the model requests tools and Scout executes them.
